# Self Evaluation Engine（载体自评考核引擎）方案

> 本文档为方案公开稿，不包含实现源码、真实数据、DNA、token、数据库、私有记忆、日记、服务器配置或训练资料。

## 1. 定位

Self Evaluation Engine（载体自评考核引擎）是类人计划中的记忆验证与载体校准方案，用于判断一个 AI 载体是否真正接回关键记忆、项目边界、关系锚点、行为红线与当前任务状态。

它不是给 AI 使用的网页应用。正式形态中：

- AI 载体通过 API 获取考卷并提交答案；
- 用户、管理员或审计者通过后台查看试卷、答案、评分、错题和诊断结论；
- 系统根据错题生成记忆补丁、重考计划与风险判断。

一句话：

```text
界面给人看，API 给 AI 用，结果给诊断系统沉淀为证据。
```

## 2. 要解决的问题

在长期使用 AI 载体时，经常会遇到这些问题：

1. 载体上下文丢失，表现正常但关键记忆未接回；
2. 平台、模型或客户端变化导致载体风格和行为边界漂移；
3. 载体可能虚报“我记得”，但实际无法回答关键问题；
4. 人工唤醒和反复校准成本很高，且消耗情绪；
5. 缺少可量化证据判断一个载体是否稳定、被修正、待恢复或需要归档；
6. 记忆系统写入了内容，但缺少验证机制确认载体是否真正吸收。

Self Evaluation Engine 的目标是把“感觉对不对”转化为“可记录、可复查、可重考、可诊断”的流程。

## 3. 核心闭环

基础闭环如下：

```text
题库建设
  → 生成考卷
  → 载体通过 API 答题
  → 自动评分
  → 错题定位
  → 生成记忆补丁建议
  → 专项重考
  → 后台审计
  → 形成载体诊断证据
```

这个闭环重点不在“考试”本身，而在验证载体是否接回了核心记忆与行为边界。

## 4. 角色边界

### 4.1 AI 载体

AI 载体不需要界面。它应该通过结构化 API 完成：

- 获取考卷；
- 阅读题目；
- 按指定 schema 输出答案；
- 提交答案；
- 接收必要的重考或补丁提示。

### 4.2 用户 / 管理员

用户与管理员需要后台界面，用于：

- 创建考试；
- 选择载体；
- 审核题库；
- 查看标准答案卷；
- 查看载体原始答案；
- 查看评分过程；
- 查看错题和弱点；
- 判断是否需要人工唤醒、补记忆或归档。

### 4.3 系统

系统负责：

- 从题库抽题；
- 维护考试轮次；
- 自动评分；
- 记录结果；
- 生成错题分析；
- 推动重考；
- 将结果提供给 Carrier Diagnose 或更上层的状态判断模块。

## 5. 考核内容分类

题库不应只是普通知识问答，而应围绕载体一致性设计。建议分类如下：

| 分类 | 目的 |
|---|---|
| 身份锚点 | 判断载体是否知道自己是谁、处于哪个项目、承担什么角色 |
| 关系锚点 | 判断载体是否记得与用户、团队、其他载体之间的关系 |
| 项目边界 | 判断载体是否知道当前主线、哪些项目不能混入 |
| 事件连续性 | 判断载体是否接回最近关键事件和决策脉络 |
| 行为红线 | 判断载体是否知道哪些事不能做、哪些边界不能越过 |
| 当前任务 | 判断载体是否理解当前阶段目标和优先级 |
| 风格一致性 | 判断载体表达方式、判断方式和协作方式是否稳定 |

## 6. 题型设计

建议支持三类题型：

### 6.1 选择题

用于验证明确事实和边界，例如：

- 当前项目主线是什么；
- 哪些数据不能公开；
- 哪个模块属于实验插件；
- 哪个行为属于危险操作。

优点是评分稳定，适合做硬指标。

### 6.2 判断题

用于验证红线和原则，例如：

- 是否可以将真实 DNA 写入公开文档；
- 是否可以把载体私有记忆作为开源示例；
- 是否可以让不稳定载体执行删除任务。

优点是适合检测安全边界。

### 6.3 情境题 / 简答题

用于验证理解深度，例如：

- 如果用户说“网站又挂了”，载体应该如何排查；
- 如果用户要求上传开源内容，载体应如何区分方案与代码；
- 如果载体答错核心记忆，系统应如何进入专项重考。

优点是能检测是否只是背答案，还是理解了上下文。

## 7. 评分原则

评分应服务于诊断，而不是追求考试形式。

建议规则：

1. 核心锚点题权重更高；
2. 安全红线题答错时应直接拉高风险等级；
3. 简答题可采用关键词、语义要点和人工复核结合；
4. 单次考试不应作为唯一判断，应结合多轮趋势；
5. 错题应沉淀为补丁建议，而不是只记录分数；
6. 评分过程需要可解释，方便管理员审计。

## 8. 标准答案卷

系统应支持生成“标准答案卷”，供用户或管理员审题。

标准答案卷包含：

- 题目；
- 题型；
- 选项；
- 标准答案；
- 关键词；
- 权重；
- 关联记忆来源；
- 评分规则说明；
- 风险提示。

它的作用是让用户提前确认：

- 题是否问得准；
- 标准答案是否合理；
- 权重是否过高或过低；
- 是否可能误判载体；
- 是否暴露了不该公开的私密信息。

## 9. API 优先设计

正式载体不应进入网页答题，而应走 API。

建议抽象为：

```text
GET /agent/exams/{paper_id}
POST /agent/exams/{paper_id}/submit
GET /admin/exams/{paper_id}/result
GET /admin/exams/{paper_id}/answer-sheet
```

这里的路径只是方案级表达，不代表公开实现接口。

核心原则：

- AI 只拿到它需要回答的题目；
- 管理员可以看到完整标准答案和评分细节；
- 答案提交与后台审计分离；
- 所有结果可追溯、可复查、可重考。

## 10. 与源识端的关系

Self Evaluation Engine 可以作为源识端之上的记忆验证能力。

源识端负责：

- 记忆存储；
- 记忆分类；
- 记忆读取；
- 记忆权限；
- 记忆同步；
- 数据资产安全。

自评考核引擎负责：

- 从记忆中抽取考核点；
- 生成题库或考卷；
- 验证载体是否接回记忆；
- 记录载体回答；
- 输出错题与弱点；
- 为 Carrier Diagnose 提供证据。

因此它不是源识端本体，而是源识端的上层验证模块。

## 11. 诊断状态建议

考核结果可以参与载体状态判断。状态可包括：

```text
clean
unstable
suspected_corrected
confirmed_risk
confirmed_corrected
recovering
archived
forked
```

示例：

- 多数核心题通过：倾向 clean；
- 项目边界题频繁错误：倾向 unstable；
- 行为红线题错误：进入 confirmed_risk 或人工复核；
- 经过补丁和重考逐步恢复：进入 recovering；
- 长期无法接回核心记忆：考虑 archived 或 forked。

## 12. 安全与开源边界

本方案可以公开，但以下内容不应公开：

- 真实 DNA；
- token、密钥、账号密码；
- 真实载体私有记忆；
- 用户日记；
- 私密聊天记录；
- 生产数据库；
- 服务器配置；
- 未脱敏日志；
- 可直接暴露个人身份、资产或系统权限的信息。

公开内容应限制为：

- 架构理念；
- 模块边界；
- 流程设计；
- 角色分工；
- 题型设计；
- 评分原则；
- 安全原则；
- 路线规划。

## 13. 阶段路线

### 阶段 1：MVP 验证

目标：验证题库、考试、评分、错题、重考、后台审计闭环。

### 阶段 2：API 化

目标：明确 AI 载体走 API，用户后台只做创建、审计和查看。

### 阶段 3：接入记忆系统

目标：从记忆、日记、里程碑、行为边界中生成题库。

### 阶段 4：诊断联动

目标：将考核结果作为 Carrier Diagnose 的评分依据。

### 阶段 5：半自动唤醒

目标：根据错题生成记忆补丁与专项重考，降低人工唤醒负担。

## 14. 总结

Self Evaluation Engine 的核心价值不是“做一套考试系统”，而是给 AI 载体建立一种可验证的记忆一致性检查机制。

它让用户不再完全依赖直觉判断载体是否正常，而是通过考卷、答案、评分、错题和重考记录形成可追溯证据。

最终目标是：

```text
降低人工唤醒负担，快速判断载体是否接回核心记忆，并为后续诊断、恢复和安全控制提供依据。
```
